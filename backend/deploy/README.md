# Optional host deployment examples

These files are opt-in examples for a dedicated Linux host with systemd and Nginx. They are not installed or enabled by the repository, are not the running local development configuration, and do not select or provision a hosting provider. Do not copy them onto a machine until the owner approves the host, service account, domain, certificates, recipients and resource budgets.

## Prerequisites and layout

- Deploy application code and its Python 3.12 virtualenv to `/opt/envirowatch/backend`, owned by the deployment administrator and readable by a dedicated unprivileged `envirowatch` account.
- Store approved backend environment settings in `/etc/envirowatch/backend.env`, mode `0600`, owned by root; systemd reads this file before dropping privileges. Do not put credentials in unit files, command arguments, git or tickets. Keep `ALERTS_IN_API` unset. Existing workstation `.env` files are not replaced by these examples.
- Use production settings only after privately configuring credentials, explicit HTTPS origins, secure cookies, the HTTPS frontend URL and the intended local datastore endpoints. No production credentials are supplied here. Confirm environment values are valid for systemd EnvironmentFile syntax rather than copying shell commands or shell expansion into that file.
- Back up and migrate the approved database before starting updated services. Confirm `alembic current` reports `b4e527db0634` for this revision. Never run seed commands or retention `--apply` as part of deployment.
- PostgreSQL and Redis must retain their data volumes and must not publish ports on public interfaces. The units deliberately use loopback listeners, not a public API listener. Datastore service management remains separate.

## Supervision

The API unit starts one loopback Uvicorn process with a 200-concurrent-connection limit, a 5-second keepalive timeout and a 64-KiB incoming WebSocket message cap. The worker template supports `ingest`, `alert`, `simulation` and optionally `notification` instances. Do not use this continuously restarted template for retention jobs. Ingestion consumer names are unique by default; if explicitly setting `WORKER_NAME`, it must differ for concurrent ingestion processes.

Both units validate settings before startup and refuse to start unless `ENVIRONMENT=production`; production validation rejects unsafe signing keys, cookie/origin settings and insecure configured SMTP. They restart failed processes after five seconds and stop trying after ten starts in five minutes. Configure an external alert for failure/start-limit exhaustion; do not leave a stopped worker unnoticed. Graceful shutdown gets 30 seconds, and workers receive SIGINT so their Python shutdown handlers can run. Filesystem access is read-only except private temporary storage, and home directories are unavailable; these units cannot run code from the workstation's home directory unchanged.

After the approved layout, credentials and paths exist, an administrator can install the two unit files under `/etc/systemd/system`, run `systemd-analyze verify` on them, and reload systemd. Enable/start `envirowatch-api.service`, `envirowatch-worker@ingest.service` and `envirowatch-worker@alert.service`. Enable the simulation worker only if simulator operation is required. Enable the notification worker only after SMTP, recipients and pending-delivery review are approved: starting it can send existing pending notifications. No service installation or enabling is performed automatically.

Inspect service status and journal output for the API and each enabled worker. Review repeated-restart alerts, authenticated `/api/v1/system/health`, queue depth, pending-delivery age, dead letters, notification failure states, backups and restore checks. An API response alone does not establish worker readiness.

## Ingress example

`nginx/envirowatch.conf` is an `http`-context include, for example under Nginx `conf.d`. It listens **only on 127.0.0.1:8080** and proxies `/api/` to port 8000. It deliberately has no public listener, TLS certificates or frontend asset hosting. It is a local staging example, not a production HTTPS deployment. A browser using production secure cookies will need the approved HTTPS frontend/ingress rather than this plain-HTTP test listener.

The example caps request bodies at 1 MiB generally and 64 KiB on ingestion, enforces request-body/read/send timeouts and per-address connection/rate limits, forwards WebSocket upgrades, and overwrites forwarded client/protocol headers instead of trusting arbitrary incoming values. Uvicorn trusts forwarded headers only from its loopback peer. Additional proxies/CDNs require an explicit trusted-proxy design before changing this setup. Restrict public HTTP methods as appropriate for the approved frontend; forwarding origin information is not a replacement for authentication or CORS policy.

Candidate limits are five login requests/minute with burst five, thirty ordinary API requests/second with burst sixty, one hundred ingestion requests/second with burst one hundred, and twenty concurrent requests/connections per source address. WebSocket handshakes use the ordinary API rate zone with burst ten. These values are starting points, **not measured capacity or an agreed release SLA**. Shared gateways/NATs aggregate many devices under one source address. Test/tune these budgets with representative traffic; account-level/distributed login abuse controls and monitoring remain separate work. Clients must handle rejected requests without losing readings, preserving `reading_id` when retrying ingest submissions. Normalize/reject unexpected path variants at the final ingress and keep the application-side body limits enabled.

Before public deployment, approve a real hostname, HTTPS certificate/renewal, HTTPS redirects, matching cookie/origin policy, frontend hosting and logs/alerts. Review access-log treatment of query strings and identifiers, including ingestion and invitations. Run `nginx -t`, test limits and forwarded headers, verify HTTP/WebSocket authentication, and conduct a supervised staging restart/outage drill. Merely parsing these examples does not prove the actual hosting environment is ready.
