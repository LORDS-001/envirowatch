# EnviroWatch implementation status

Updated: 2026-11-23. This records the local implementation and verification, not approval to deploy. No completion percentage is assigned, and the review is not exhaustive.

## Outcome

The real backend now implements the principal UI contracts: authenticated fleet management, queued ingestion and live updates, quality-aware maps and reports, alert evaluation, invitations, publication-controlled public data, an isolated persistent simulator, and explicit retention/rollups. Mock mode remains a separate demonstration, not evidence of real-service functionality.

Core regression coverage now includes PostgreSQL, Redis, workers and a real browser rather than only mocked responses. Production readiness remains blocked by security configuration, operational setup, measured scale/detector acceptance, and the incomplete capabilities listed below. Do not deploy using the existing local credentials or assume starting the API starts the workers.

## Recovered purpose and rules

EnviroWatch is an environmental sensor monitoring application. Operators inspect trusted current readings, maps, historical analytics, pollution alerts and device faults; administrators manage devices, sites, accounts, alert rules, retention and evaluation runs. Anonymous visitors see only explicitly published environmental data.

Sources recovered: root README, `docs/FRONTEND_PLAN.md`, `docs/API_GAPS.md`, `docs/DECISIONS.md`, design tokens/principles, frontend contracts, backend migrations and implementation. Documented conventions include a 10-second nominal sensor cadence, a 30-second freshness budget, quality/time/unit disclosure, labeled non-color-only states, chart table alternatives, tenant isolation, admin-only mutations, memory-only access tokens, and an httpOnly refresh cookie. Existing libraries and components were reused; ReportLab supplies PDF generation rather than a custom PDF encoder.

No applicable `AGENTS.md` was found. The original PRD, complete kickoff brief/`CLAUDE_CODE_PROMPT.md`, and original backend completion plan could not be recovered. The frontend plan itself records a truncated original input and missing design artifacts; its historical decisions remain evidence, not newly recovered files. Product-wide acceptance criteria cannot be certified against an unavailable original PRD. Recommendations below are labeled separately from recovered behavior.

The owner's instructions take precedence over repository text. Existing uncommitted work was preserved, including the emptied ground-truth file and local logs. No commit, push, production deployment, system software installation, external email, retention deletion, credential rotation or public publication was performed. Only project-virtualenv PDF dependencies were installed during approved implementation. Tests use isolated schemas/Redis namespaces and disable external delivery.

## Delivered changes

- Setup: Node version pin, repaired Python requirements, real-backend Vite proxy, configurable test browser, separate workers and documented setup. Approved local maintenance has now recreated PostgreSQL/Redis with loopback-only ports and their original images, commands and named volumes; both services are healthy.
- Contracts: paginated fleet/sites/alerts/events, validated aggregate envelopes and time windows, real site creation, global fleet search, historical suspicious-data selection, correct null health handling, and co-located-map projection safety.
- Session/security: coalesced refresh, bounded authenticated retries, session data/cache/socket cleanup, immediate device-key revocation, locking for sensitive mutations, production configuration checks, and one-time expiring/reissuable invitation links with password setup. Secrets and invitation tokens are not logged.
- Backend hardening: bounded HTTP bodies before JSON parsing (64 KiB ingest, configurable 1 MiB default elsewhere), explicit production HTTPS origins, atomic acknowledgement/deletion of pending stream deliveries, continued reclaim scans, distinct default worker consumers, Redis startup recovery, transient database recovery for notification/simulation loops, and persisted bounded email retry scheduling with stable Message-IDs and delivery-row locking.
- Data trust/reliability: bounded atomic enqueue without trimming accepted pending work, spatial/persistent-drift classification before storage, latest-per-device freshness, consecutive corroborated alert intervals, unusual-change rules, no false resolution on silence, and honest notification states.
- Missing workflows: real CSV/PDF export, explicitly allowlisted public endpoints, persistent isolated simulator and worker, and transactional retention with weighted hourly/daily summaries. Saving a retention policy does not enable deletion.
- Verification: backend contract/workflow/migration/reliability tests, browser integration against actual PostgreSQL/Redis/workers, and a CI workflow using disposable services. Remote CI is not yet verified.

Implementation assumptions requiring domain acceptance, not recovered PRD requirements: unusual-change uses a preceding-hour median with at least ten samples; peer outlier/drift heuristics use fixed margins and persistence; simulator scenarios use 12 sensors and accelerated virtual time. The nominal cadence/freshness conventions were recovered, but these particular detector choices must not be presented as scientifically validated thresholds.

## Dependency-ordered completion plan

1. **Secure and reproduce the local/staging environment** — Outcome: safe reproducible runtime. Local migration head and loopback-only datastores are verified, with original volumes preserved. Monitor/investigate recurring host I/O stalls, complete the dependency advisory scan, privately rotate production secrets/accounts, choose staging target and supervision, adapt the opt-in examples, and execute CI. Prerequisites: owner's access/deployment decisions and stable host storage. Acceptance: migration head, full checks, no publicly exposed datastore ports, supervised recovery and a verified backup/restore. Effort: small–medium for application setup; host troubleshooting is uncertain and not authorized as a system change.
2. **Close data correctness acceptance** — Outcome: defensible trusted/expected-reading statistics. Calibrate classifiers with labeled samples, define missing-reading cadence/history, implement and validate accounting, and approve any reversible historical backfill. Components: ingestion, faults/health, device lifecycle, quality summary, analytics and reports. Acceptance: labeled precision/recall, missing-count boundary fixtures, retained/raw consistency. Effort: medium–large; uncertainty: domain policy and available ground truth.
3. **Complete required delivery and publication** — Outcome: approved users/recipients/public sites receive only intended information. Configure and test invitation/email delivery, add retry/idempotency, decide whether SMS/webhooks and site-level publication are requirements. Acceptance: real non-production invitation and delivery, failure/retry/tenant tests, anonymous export privacy. Effort: medium for email; larger if new transports or fine-grained publication are required. Those additions are scope decisions, not silently assumed requirements.
4. **Make background processing operable** — Outcome: bounded storage and recoverable workers. Approve and schedule retention, add sandbox cleanup/quotas, monitoring and outage reconciliation. Components: workers, retention, simulator, deployment configuration. Acceptance: restart/broker outage drills, no accepted-message loss in the agreed guarantees, no cross-tenant cleanup, restore and rollup verification. Effort: medium; uncertainty: retention and delivery guarantees.
5. **Prove release readiness** — Outcome: measured acceptance rather than a passing build. Run sustained representative load, detector evaluation, manual accessibility/responsiveness and targeted security tests; fix measured bottlenecks. Acceptance targets must be agreed where the original PRD is unavailable. Effort: medium–large; uncertainty: production scale, detector thresholds and external services. Deploy only after these gates and separate deployment authorization.
